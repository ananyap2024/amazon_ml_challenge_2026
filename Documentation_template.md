## 1. Executive Summary

We present an end-to-end, high-precision Business Entity Resolution pipeline designed to link multi-source business records from Source 2 and Source 3 to the deduplicated reference Source 1 under severe scale, extreme class imbalance, and heterogeneous real-world noise. Our solution employs a decoupled two-stage architecture: (1) a token-frequency-calibrated inverted index blocking engine developed by Member 1 that reduces the quadratic comparison space (over 50 trillion potential pairs) down to a high-recall candidate set; and (2) a 13-feature gradient-boosted decision tree classifier (XGBoost) engineered by Member 2 that captures character-level edit distance, token Jaccard overlap, sequence similarity, length ratios, and corpus-level TF-IDF cosine semantics across business names and addresses without external lookup dependencies.

Validated using strict 5-fold entity-grouped cross-validation (`GroupKFold`) across 2,408,157 realistic candidate pairs derived from a 1,000-entity Source 1 sample, our production XGBoost model achieved an **OFFLINE 5-fold GroupKFold Macro Entity-Level $F_{0.5}$ validation score of 0.7283 (72.83%)** with a Macro Entity Precision of **0.7495 (74.95%)** at the primary validation-supported threshold candidate of **0.60** (rather than a guaranteed final leaderboard threshold). The matching system is accompanied by a memory-conscious streaming/chunked batch inference driver (`batch_inference.py`) designed to score large candidate sets in constant memory, outputting continuous match probabilities and thresholded classifications for Member 3's final post-processing, threshold selection, and submission packaging.

## 2. Methodology

### 2.1 Problem Analysis

Exploratory Data Analysis (EDA) across the three heterogeneous data sources revealed critical structural complexities, noise patterns, and operational constraints:

1. **Severe Combinatorial Scale vs. Intractable Pair Space:**
   Source 1 contains approximately 2.2 million reference entities, while Source 2 and Source 3 each contain over 5 million records. A naive Cartesian comparison ($|S_1| \times (|S_2| + |S_3|)$) yields over $2.3 \times 10^{13}$ pairwise comparisons, making exhaustive matching computationally infeasible. An aggressive, high-recall blocking stage is strictly required.

2. **Heterogeneous Name Noise and Semantic Aliasing:**
   Business names exhibit heavy abbreviation variations (e.g., *Corp* vs. *Corporation*, *Pvt* vs. *Private*, *Ltd* vs. *Limited*, *LLC*, *Inc*), legal suffixes, trade names (DBA), punctuation differences (*&* vs. *and*), and word order permutations. Generic tokens dominate corporate titles, which can artificially distort similarity metrics if not properly handled.

3. **Unstandardized and Incomplete Address Structures:**
   Business addresses lack standardized postal structuring. Key noise elements include landmark-based descriptions (e.g., *"Near SBI ATM, Main Road"*), missing PIN/postal codes, missing state or municipal identifiers, and erratic token orderings. Character-only distance metrics degrade on reordered address tokens, requiring token-based and TF-IDF semantic metrics.

4. **Open-Set Country Distribution (The France Test Shift):**
   The training data only covers `US` and `India`, whereas the test set introduces a third country, `France`, which never appears in the training corpus. Consequently, the pipeline must strictly avoid closed-world one-hot encodings or hardcoded country filtering. Country similarity is engineered as an open-set relational binary equality feature (`country_same`), remaining robust to unseen country labels.

5. **Extreme Class Imbalance in Realistic Candidate Spaces:**
   In the realistic candidate space generated by blocking, true matching pairs account for approximately **0.0991%** of candidate pairs (~1 true match per 1,000 candidates). Models trained on artificially balanced (50/50) sets fail to calibrate probabilities under this distribution without rigorous threshold tuning on realistic data.

6. **Precision-Heavy Objective Function ($F_{0.5}$ Metric):**
   The competition evaluates solutions using the Macro Entity-Level $F_{0.5}$ score:
   $$\beta = 0.5 \implies F_{0.5} = \frac{(1 + 0.5^2) \times \text{Precision} \times \text{Recall}}{0.5^2 \times \text{Precision} + \text{Recall}} = \frac{1.25 \times \text{Precision} \times \text{Recall}}{0.25 \times \text{Precision} + \text{Recall}}$$
   In enterprise master data management, merging two distinct commercial entities (a false positive) incurs high risk and severe business degradation, whereas missing a link (a false negative) simply leaves records unlinked. Thus, $F_{0.5}$ weights precision twice as heavily as recall ($\beta = 0.5$). Furthermore, the macro-average explicitly scores singletons (Source 1 entities with zero true matches) as $1.0$ when correctly left empty and $0.0$ if any false match is predicted. High precision is therefore the paramount optimization target.

**Core Technical Innovations:**
1. **Frequency-Capped Distinctive Inverted Indexing:** Rather than indexing all tokens (which causes explosive candidate sizes on words like "India" or "Enterprises"), candidate generation indexes words filtered by an empirical frequency ceiling (`max_frequency = 5000`) and prioritizes the rarest distinctive tokens, yielding high recall with bounded pair counts.
2. **Unified 13-Feature Statistical and Edit-Distance Representation:** A comprehensive feature vector combining string edit distance (Levenshtein), character block similarity (`difflib.SequenceMatcher`), token-level Jaccard overlap, relative length ratios, open-set country equality, and word-level TF-IDF cosine vectors fitted exclusively on development training text.
3. **Decoupled Streaming/Chunked Architecture:** The production inference driver (`batch_inference.py`) indexes source records into memory hash tables once, processes candidate pairs in streaming chunks (default 10,000), and outputs match probabilities. This decouples heavy ML feature extraction and probability scoring from final threshold selection, providing Member 3 with full flexibility during post-processing.

### 2.3 Training Data Construction & Validation Split Methodology

To train and evaluate the matching model without data leakage or distribution distortion, data preparation followed a disciplined two-phase methodology:

1. **Initial Supervised Development Dataset (Balanced Pair Benchmark):**
   - **Positive Pairs:** Generated by exploding `train_ground_truth.tsv` where `matched_entity_ids` was non-empty, and extracting 10,000 true positive matching pairs (`(S1, S2)` and `(S1, S3)`) using `random_state=42`.
   - **Negative Pairs:** Generated by taking the exact Source 1 entities from the positive sample and pairing them with randomly sampled candidates from Source 2 and Source 3 (`random_state=42`), followed by strict exclusion filtering against the complete ground truth table to ensure zero false negatives in the negative set.
   - **Combined Development Set:** 20,000 pairs (10,000 positive, 10,000 negative; exactly 50% positive rate).
   - **Train / Validation Split:** Split at the entity level into 80% training (16,002 rows across 7,981 Source 1 entities) and 20% validation (3,998 rows across 1,996 Source 1 entities). The name and address TF-IDF vectorizers were fitted strictly on this 16,002-row development training split.

2. **Realistic Candidate Evaluation Dataset (2.4M-Row Imbalanced Benchmark):**
   - To evaluate how models perform in realistic inference conditions (where candidate generation produces thousands of non-matches per entity), a dedicated evaluation sample of **1,000 Source 1 entities** was drawn from `train_ground_truth.tsv` (`random_state=42`, selecting entities with non-empty ground truth matches).
   - Member 1's blocking pipeline was executed against the full Source 2 and Source 3 training datasets for these 1,000 entities, generating **2,408,157 candidate pairs**.
   - These candidate pairs were labeled against the ground truth: **2,386 positive pairs (label 1)** and **2,405,771 negative pairs (label 0)**, yielding an authentic class balance of **0.0991% positive rate**.
   - All 13 production features were extracted across the full 2,408,157 rows using multi-worker parallel chunk processing with strict numeric verification against single-thread outputs.

3. **Entity-Level Cross-Validation Design (`GroupKFold`):**
   - Naive row-level K-Fold cross-validation causes massive data leakage in entity resolution because candidate pairs from the same Source 1 entity appear in both train and validation folds.
   - We utilized **5-fold `GroupKFold`** grouped on `source1_entity_id`, ensuring complete isolation: no Source 1 entity present in training ever appeared in validation.
   - Empirical splitter verification confirmed `GroupKFold` outperformed `StratifiedGroupKFold` on this dataset by maintaining near-perfect row-count balance (spread of 1 row vs. 154,281 rows) and lower fold positive-rate variance ($3.21 \times 10^{-5}$ vs. $1.20 \times 10^{-4}$).

## 3. Candidate Generation (Blocking)

*Implemented by Member 1.*

The candidate generation stage bridges the raw multi-million record tables and the pairwise ML model, drastically reducing the search space while preserving true positive matches.

- **Blocking Keys Used:**
  1. **Unicode-Normalized Exact Name Index:** Text is normalized using NFKC Unicode normalization, lowercased, stripped of non-alphanumeric punctuation and symbols, and stripped of explicit missing tokens (`"nan"`, `"none"`, `"null"`). An exact inverted index maps `name_norm -> {entity_ids}`.
  2. **Tokenized Business Name Inverted Index:** Normalized business names are split into discrete word tokens.
  3. **Stop-Token and Length Filtering:** Generic corporate suffixes and business descriptors that provide negligible discriminative power are filtered out via `GENERIC_NAME_TOKENS` (`"private"`, `"limited"`, `"ltd"`, `"llc"`, `"inc"`, `"incorporated"`, `"corp"`, `"corporation"`, `"company"`, `"co"`, `"plc"`, `"pvt"`, `"public"`). Tokens shorter than 3 characters are discarded.
  4. **Frequency Capping & Distinctive Token Selection:** For each token in the inverted index, document frequency across the candidate corpus is computed. When querying candidates for a Source 1 entity, tokens exceeding `max_frequency = 5000` records are pruned. The remaining tokens are sorted by frequency (rarest first), and up to `max_tokens = 3` distinctive tokens are queried.

- **Candidate Pairs Generated:**
  - **Full Test Set Candidate Pairs:** **161,521,156 candidate pairs** generated across 9,966 test Source 1 entities in `candidate_pairs_internal.tsv` (80,102,731 from Source 2; 81,418,425 from Source 3). This represents the blocking output set produced by Member 1 to be fed to inference.
  - **Test Candidate Distribution Per Entity:** Minimum = 1, Median = 12,910, Mean = 16,207, 75th percentile = 27,489, 90th percentile = 38,880, Maximum = 78,374 candidate pairs.
  - **Realistic Train-Side Calibration Sample:** **2,408,157 candidate pairs** across 972 unique Source 1 entities from a 1,000-entity sample (1,400,454 from Source 2; 1,007,703 from Source 3; median = 1,655; mean = 2,408; max = 17,419).

- **How You Ensured True Matches Were Not Lost:**
  - **Multi-Key Union Strategy:** For every Source 1 entity, the candidate set is formed by the set union of:
    $$\text{Candidates}(S_1) = \text{ExactName}(S_1) \cup \text{TokenCandidates}(S_1, \text{token}_1) \cup \text{TokenCandidates}(S_1, \text{token}_2) \cup \text{TokenCandidates}(S_1, \text{token}_3)$$
    Even if an entity name undergoes token reordering, prefixing, or contains a minor typographical error in one token, the independent exact and secondary token lookups retrieve the record.
  - **Empirical Recall Ceiling Calibration:**
    On the 1,000-entity train ground truth sample, the blocking mechanism retrieved **2,386 out of 3,710 true matches**, establishing an empirical blocking recall ceiling of **64.31%** (65.67% on Source 2, 63.03% on Source 3).
    All true matches were fully recovered for 412 entities, partial matches were retrieved for 412 entities, and zero candidates were retrieved for 176 entities. Missed candidates primarily stemmed from radical name discrepancies (e.g., trade name vs. legal parent name) or landmark-only descriptions where no shared distinctive tokens existed.

## 4. Matching Model

*Implemented by Member 2.*

The pairwise matching stage computes granular similarity vectors across candidate pairs and scores match probabilities via a gradient-boosted decision tree ensemble.

### Features Used (The Production 13-Feature Set)

The production feature matrix is strictly ordered and verified as `FEATURE_NAMES_13` in `features_13.py`:

```
+----+--------------------------------+-----------+-------------------------------------------------------------+
| #  | Feature Name                   | Target    | Mathematical Formulation / Logic                            |
+----+--------------------------------+-----------+-------------------------------------------------------------+
| 1  | name_exact                     | Name      | 1 if norm(name_1) == norm(name_2) and non-empty, else 0     |
| 2  | name_similarity                | Name      | difflib.SequenceMatcher ratio: 2M / (len_1 + len_2)         |
| 3  | address_exact                  | Address   | 1 if norm(addr_1) == norm(addr_2) and non-empty, else 0     |
| 4  | address_similarity             | Address   | difflib.SequenceMatcher ratio on normalized addresses       |
| 5  | country_same                   | Country   | 1 if norm(c_1) == norm(c_2) and non-empty, else 0 (open)   |
| 6  | name_token_overlap             | Name      | Jaccard index: |tokens_1 & tokens_2| / |tokens_1 | tokens_2|   |
| 7  | address_token_overlap          | Address   | Jaccard index on whitespace-delimited address tokens         |
| 8  | name_length_similarity         | Name      | 1 - |len_1 - len_2| / max(len_1, len_2)                         |
| 9  | address_length_similarity      | Address   | 1 - |len_1 - len_2| / max(len_1, len_2)                         |
| 10 | name_levenshtein_similarity    | Name      | 1 - edit_distance(name_1, name_2) / max(len_1, len_2)       |
| 11 | address_levenshtein_similarity | Address   | 1 - edit_distance(addr_1, addr_2) / max(len_1, len_2)       |
| 12 | name_tfidf_cosine              | Name      | Cosine similarity of L2-normalized word TF-IDF vectors      |
| 13 | address_tfidf_cosine           | Address   | Cosine similarity of L2-normalized word TF-IDF vectors      |
+----+--------------------------------+-----------+-------------------------------------------------------------+
```

*Feature Properties:*
- **Preprocessing Continuity:** Missing values (`NaN`) follow the established normalization quirk (converted to string `"nan"` prior to tokenization), maintaining strict compatibility between training data and inference inputs without distribution shift.
- **Open-Set Country Robustness:** `country_same` evaluates string equality dynamically. It does not assume a closed category set of `{US, India}`, ensuring seamless generalization to test records from `France`.
- **Pre-Fitted TF-IDF Vectorizers:** TF-IDF models (`TfidfVectorizer(analyzer="word", token_pattern=r"(?u)\b\w+\b", lowercase=False, norm="l2")`) were fit strictly on the development training split (16,002 pairs) and persisted to `models/tfidf_vectorizers.pkl`. They are loaded as immutable artifacts during inference and never refit on test data.

### Model Architecture & Hyperparameters

- **Model Type:** Extreme Gradient Boosting (`XGBClassifier` from `xgboost==3.2.0`).
- **Production Hyperparameters:**
  ```python
  xgb_params = {
      "n_estimators": 300,
      "learning_rate": 0.05,
      "max_depth": 4,
      "min_child_weight": 1,
      "subsample": 0.8,
      "colsample_bytree": 0.8,
      "reg_lambda": 1.0,
      "objective": "binary:logistic",
      "eval_metric": "logloss",
      "tree_method": "hist",
      "random_state": 42,
  }
  ```
- **Architectural Rationale:**
  - Non-linear decision trees capture essential cross-feature interactions (e.g., verifying that moderate name similarity is acceptable if address TF-IDF cosine is exceptionally high, or confirming that high token overlap in names requires non-zero address overlap).
  - The `hist` tree method provides fast histogram-based partitioning across large data tables while remaining within compact CPU/memory constraints.
  - Shallow tree depth (`max_depth=4`) combined with conservative feature and row subsampling (`0.8`) and shrinkage (`learning_rate=0.05`) prevents overfitting on dominant corporate naming templates.

### Threshold Selection Method

- We performed a systematic threshold sweep from $\tau = 0.05$ to $\tau = 0.95$ in increments of $0.05$ across all 5 folds of the realistic candidate distribution (2,408,157 pairs).
- Macro Entity-Level $F_{0.5}$ was computed at every threshold step using the competition formula, scoring singletons and calculating per-entity precision and recall.
- **Primary Supported Threshold Candidate:** **$\tau = 0.60$**.
  - Threshold 0.60 achieved the peak OFFLINE 5-fold GroupKFold Macro Entity-Level $F_{0.5}$ validation score of **0.7283**, lifting entity precision to **74.95%** while retaining **70.32%** entity recall.
  - Multi-seed split stability evaluations across 4 independent random seeds (42, 43, 44, 45) confirmed that optimal thresholds consistently clustered tightly in the range $[0.55, 0.65]$ (mean 0.625, std 0.065), demonstrating stability across differing entity holdouts.
  - **Note on Final Selection:** Threshold 0.60 represents the primary validation-supported threshold candidate based on offline cross-validation evidence, rather than a guaranteed final leaderboard threshold; final threshold confirmation and submission generation across the test set are managed by Member 3.

### 5.2 Error Analysis

Inspection of classification false positives and false negatives on the validation folds highlighted several distinct error modes:

1. **Common False Positives (Wrong Merges):**
   - **Multi-Branch Chains & Franchises:** National retail, hospitality, or banking chains (e.g., fast food franchises, bank branches) that share identical brand names and identical city/state designations, but represent different physical branch locations on different streets.
   - **Multi-Tenant Commercial Complexes:** Unrelated businesses located in the same office building, IT park, or industrial estate. When business names are short or generic, high address similarity can trigger false merges.
   - **Shared Corporate Acronyms:** Companies sharing identical three-letter acronyms operating in related commercial hubs.

2. **Common False Negatives (Missed Matches):**
   - **Candidate Blocking Misses (The Upstream Ceiling):** In the 1,000-entity evaluation sample, an average of 15.6% of Source 1 entities had zero true positive records present in their candidate sets. Because the matching classifier only evaluates candidate pairs supplied by Stage 1, these matches are permanently unreachable.
   - **Landmark Descriptions vs. Postal Addresses:** Cases where Source 1 lists a formal postal address (e.g., *"Plot 14, Phase 2, Industrial Area, Bangalore 560058"*) while Source 2 lists a colloquial landmark description (e.g., *"Near Peenya Police Station, Outer Ring Road"*). Token overlap and TF-IDF cosine are near zero despite referring to the same facility.
   - **DBA Names vs. Registered Legal Names:** Holding company entities linked to consumer-facing trade names (e.g., *"Tata Sons"* vs. *"Croma Electronics"*). Without external knowledge lookups (which are strictly prohibited), lexical and TF-IDF features cannot bridge radical vocabulary shifts.

## 6. Conclusion

Our solution resolves multi-source business entity fragmentation through a coordinated two-stage pipeline combining token-frequency-pruned inverted index blocking with a 13-feature gradient-boosted decision tree (XGBoost) classifier. Evaluated across 2.4 million realistic candidate pairs under authentic class imbalance (0.099% positive rate), our model achieved an **OFFLINE 5-fold GroupKFold Macro Entity-Level $F_{0.5}$ validation score of 0.7283** at the primary validation-supported threshold candidate of **0.60**, prioritizing high precision (74.95%) to protect master data integrity against false merges. The pipeline operates strictly offline without prohibited external APIs, conforms completely to MIT/Apache 2.0 licensing, and provides a scalable, streaming/chunked batch inference driver prepared for submission execution.

   - Reads candidate pairs in configurable streaming chunks (default 10,000), evaluates all 13 features on the fly, computes XGBoost probabilities, and streams output rows to disk.
   - Memory consumption remains constant throughout execution.

3. **Post-Processing & Submission Formatting (Stage 3 - Member 3):**
   Member 3 performs final pipeline execution and post-processing: applying the chosen decision threshold, grouping the predicted matches by `source1_entity_id`, formatting matched IDs as comma-separated lists, and ensuring every test Source 1 entity is represented (leaving `matched_entity_ids` empty for singletons).

4. **Submission Validation:**
   Validate both output files prior to leaderboard upload using the official validator:
   ```bash
   python utils/validate_submission.py \
       --matching output/matching_results.tsv \
       --candidate output/candidate_pairs.tsv \
       --test-dir dataset/test
   ```
